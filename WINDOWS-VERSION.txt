  数据目录终于有了可回滚的快照能力——这是本项目唯一一直没做的运维面。
  - 一键备份到 `<数据目录>/../backups`（**在数据目录之外**）。

零·上一轮、0.9.8 变更
======================================================================
定位：仅 LLM 转发。**本项目不跟进上游的图片生成与语音转写**，
「媒体实测」页从侧栏移除（代码保留，后续要跟进时加回 nav 一行即可）。

1. 检查更新卡片
   删掉「更新源 XX 前检查过 · 后台每 6 小时自动检查」那串灰字——机制是内部实现，
   用户只要结论。现在只留「上次检查：X 分钟前」，需要自行判断新旧时有用。
   新增「程序打开时检查」：首查延迟 40 秒 → 6 秒（实测这个点首屏已画完，
   不与「拉模型目录 / 供应商探测」抢网络）。之后仍每 6 小时一次。

2. 强制更新状态固化（关键修复）
   原来强制态靠 `.update-cache.json` 承载，而那份缓存 30 分钟就过期、每次检查整份覆盖。
   后果：断网一次、或清单被人改回同版本，闸门就自己开了。
   现在新增独立闸门文件 `.update-gate.json`（数据目录下）：
     • 判定为强制时写入（记 requiredVersion / installedVersion / reason）
     • **只在 APP_VERSION ≥ requiredVersion 时删除** —— 这就是解锁条件
     • 开机先读它，命中则网关那步根本不会执行（连端口都不会监听）
   并且**强制态出现后停掉整个 6 小时定时器**：已经判定必须更新，继续打 GitHub 没意义。
   被强制的用户重启多少次都解不开，装到足够新的版本才恢复。

3. 关闭按钮语义（真 bug 修复）
   标题栏 X 原来调 `Owner.Close()`，而 `Form.Close()` 的 `CloseReason` 是 `None`、
   不是 `UserClosing`，于是 `OnFormClosing` 里「UserClosing 才收进托盘」的分支不命中
   → 直接真退出，`finally` 里的 `ServerLauncher.Stop()` 连后端一起杀掉。
   用户看到的就是「点 X 后台服务没了、右下角托盘图标也消失」。
   修法：① 标题栏改走显式 `HideToTray()`；② `OnFormClosing` 不再依赖 CloseReason，
   任何非强制关闭一律收进托盘。**真退出只剩托盘菜单「退出」一条路**。
   强制更新弹窗里的「退出应用」也随之改名「关闭窗口」（它现在只隐藏窗口）。

零·上一轮、0.9.7 变更：自定义供应商出图
======================================================================
问题  自定义供应商能出图吗？不能 —— `CustomProvider.supportsImageGeneration` 恒为
      继承默认 false，于是 `/v1/images/generations` 的候选表里永远只有 antigravity，
      而本机 antigravity 0 账号 → 媒体实测页的出图永远是
      「没有支持图片生成的供应商可用」。上一版给这家供应商补了转写，出图这一半仍是断的。

改动  config 加一列 `imageModels`（默认空 = 不支持出图，与升级前行为完全一致）
      core/provider/custom/CustomProvider.kt
        覆盖 `supportsImageGeneration` = config.supportsImage
        实现 `generateImage`：POST `<base>/images/generations`，客户端原始 JSON 体直通
        **不做模型归一化**：`custom:` 下的模型名就是上游真名，resolveModel 的 auto
          回落会挑到目录里第一个模型，那多半是文本模型 —— 等于凭空编造
        取模型优先级：网关解析出的 model → 原始体里的 model → 配置里第一个图像模型
        解析 data[]：b64_json 与 url 都认（Antigravity 只给 base64，中转站常给外链）
        normalizeBaseUrl 新增剥 `/images/generations` 尾巴
      server/UiRoutes.kt
        GET /ui/custom 增加 supportsImage / imageCount / imageModels / imageEndpoint
        POST /ui/custom/save 接收 imageModels；**请求没带该字段时保留原值**
          （旧前端或第三方脚本只传 models，直接当空数组会清掉已配好的出图能力，
            症状是「编辑一次供应商，出图就坏了」）
      server/MediaProbe.kt
        `/ui/media/image` 原来只认 b64_json，上游只回外链时界面上「出图成功但看不到图」
        现在 b64 与 url 都转成 dataUrl（url 直接透传，不伪造）
      web/dist/app.js
        表单新增「图像模型」多行框（占一行，不跟别的字段挤）
        列表条目加「出图 N」标签
        媒体实测页空态归因分两句：内置供应商没能力 / **自定义供应商没填图像模型**
          （这两句混成一句时用户会去账号页翻，而问题在配置里）

顺手修的真 bug（core，带 [aigw-patch]）
      镜像响应体的 `response_format` 标记错判
      原先只要客户端要 `url` 就无条件写 `response_format: "b64_json"`。
      实测：客户端要 url、上游确实回了 http 外链、响应里也真有 url，
      却仍被标成 b64_json —— 客户端按该字段当 base64 解析，直接失败。
      改成：只有「要 url 但实际只给了 base64」时才标降级；真有外链时保持沉默。

验证  单测 core/src/test/.../custom/ImageGenerationProviderTest.kt 10 项全过
      端到端（真网关 + 两个真桩，side 有 POST 日志作独立证据）

            ui_custom_walk 13 步全过、0 异常 0 溢出
            ui_walk 12 页全过（见下方「巡检自身修复」）

      更新清单 force=true 且本机版本≤清单版本时，概览页立刻弹**不可关闭**的强制窗，

一、0.9.6 变更：免服务器强制更新（上一轮）
======================================================================
更新源  github.com/Squemadylan/AI-Gateway-updata  根目录 update.json（raw CDN，无需任何后端）
下载页  pan.quark.cn/s/8fd93162bcab              客户端点「立即更新」跳这里

链路  server/UpdateChecker.kt
  raw 优先 → Contents API 兜底 → 都失败则放行（不拦用户）
  判定  版本严格更高 且 (force=true 或 低于 minVersion) 且 downloadUrl 非空
  缓存  内存 30 分钟 + 数据目录 .update-cache.json 落盘（重启免等 8 秒超时）
  调度  Main.scheduleUpdateCheck：启动后 40 秒首次，之后每 6 小时
  端点  POST /ui/update/check?refresh=1（手动强制刷新，绕过缓存）

界面  web/dist/app.js
  概览页版本条（永远显示）：当前版本 · 状态徽标 · 检查更新 / 下载新版
  强制态：徽标转警示色、隐藏「检查更新」、按钮变「立即更新」、
          并立刻弹出不可关闭弹窗（只有「退出应用」和「立即更新」两个出口）
  心跳  每拍读 state.update；强制结果在非概览页也会弹
  失败态 显示「检查失败」+ 仍可手动打开下载页，绝不弹强制窗

强制 = 真的不能用（0.9.7 补的，之前只弹窗不禁服务）
  关键认识：窗口只是拦截的一层，客户端完全不需要理会它 —— Cursor / Claude Code
  这类工具直接请求 127.0.0.1:8790/v1 就照常能用。只弹窗的「强制」等于没有强制。

  服务端闸门  UpdateChecker.gateClosed（一旦落位在进程内不可撤销）
    Main.startGateway       闸门已落则**根本不监听端口**（不是起来再停，无中间窗口期）
    Main.scheduleUpdateCheck 后台查出强制更新后立刻 enforceGate() 停网关
    EngineHost.snapshot()   每拍心跳顺带 enforceGate()，2 秒内必然停掉活着的网关
    POST /ui/gateway/start  被拒（否则用户点一下「启动」就绕过整道闸）
    落盘缓存重启也生效        .update-cache.json 里 mandatory=true 时开机即落闸

  界面锁（web/dist/app.js lockShell）
    .gate-cover 盖板 z-index 900（低于 modal-mask 1000，弹窗浮在上面）
    .shell 加 inert 属性：屏幕点不到（pointer-events）+ Tab 键盘也进不去
    已实测 elementFromPoint 命中侧栏每一项都返回 modalMask，nav.focus() 无效
    锁解除只在服务端 gateClosed 转 false 时发生（即装完新版重启后）

  验证记录（临时实例 + 预置强制缓存）
    running=false / gateClosed=true / 日志「强制更新闸门已落，网关不启动」
    netstat 无网关端口；curl 直连 → Connection refused
    POST /ui/gateway/start → ok:false「必须更新才能启动网关（当前 0.9.7，0.9.8 已发布）」
    盖板 hit-test：overview/logs/providers/accounts 全部 → modalMask

发布新版流程
  1. 打包 AI-Gateway-Windows-<版本>.zip 上传夸克网盘（链接长期复用）
  2. 改 AI-Gateway-updata 仓库 update.json 的 version / downloadName / notes
  3. commit + push；客户端最长 6 小时自动看到，手动点「检查更新」立刻看到
  4. 本仓库 EngineHost.kt 的 APP_VERSION 必须同步升，否则新装版本会一直提示更新
  5. **force=true 时任何人都跑不起来**：想只提示不锁死，设 force=false 并靠 minVersion
     卡必须升级的下限版本；闸门落下后同进程无法解除，用户必须装新版重启才能恢复

六b、Auto 智能路由（0.5.0 新增，参考 FreeLLMAPI 方案）

六·h  0.7.0 —— 交互性能专项（拖动/卡顿/余额）

一、概览布局
  1. 「消耗趋势」与「最近调用」改为左右并排（与上方「实时调度拓扑 / 上下文容量分布」
     同一套 EqualColumnsLayout(2) 分配，窄窗口两栏都保底、不裁切）。

二、拖动与缩放（四条独立缺陷）
  1. 每个 mouseDragged 直接 frame.setLocation → 改为 16ms 帧合并（status: pendingBounds
     + Timer），一帧最多一次 SetWindowPos。原先一次拖动可在 EDT 上排上百次同步改窗。
  2. 拖动坐标改用 MouseInfo 真实光标（事件坐标作兜底，差异 >200px 视为不可信）。
     原实现用 MouseEvent.getXOnScreen，该值 = 窗口位置 + 客户区坐标，窗口一跟手就被
     补偿，形成「窗口追光标 → 坐标漂移 → 追不上」的反馈环，表现为抖动与「拖两下拖不动」。
  3. 拖动/缩放期间挂起全部界面刷新（suspendUiRefresh），松手补一帧。
  4. release 丢失自愈：mouseMoved/mouseDragged 检测到左键已抬起即复位 titleDrag / mode，
     修掉「拖两次之后整个窗口再也拖不动」的残留状态。
  5. 位置更新区分「只挪位置」与「改尺寸」：尺寸不变走 setLocation，不复用 setBounds
     （后者即使尺寸相同也会触发容器重排）。

三、Aero Snap 坐标修正
  snapEdgeOf / snapToHalf 改用显示器**虚拟桌面绝对坐标**（b.x + ins.left / b.y + ins.top）。
  原实现按 ins.left 与 0 计算，多显示器（非主屏原点不为 0）时贴边会把窗口吸到主屏，
  即「贴边时窗口位置乱跳」。

四、界面刷新降负（EDT）
  1. refreshAll 增加 200ms 节流；动作类操作（刷新额度/拉模型/启停/切页）走 force 跳过，
     避免动作后的刷新被节流吞掉（这正是「点了刷新额度但数字不变」的一个成因）。
  2. 表格改 syncModel 差异更新，不再 rowCount=0 + 逐行 addRow（后者每拍触发
     structureChanged → 列宽重置 + 选中丢失 + 整表重绘）。且只同步当前可见页的表格。
  3. 「最近调用」按记录签名比对，无变化不重建组件。
  4. 日志页：不在该页时完全跳过；在页时用「头部 insert + 尾部裁剪」增量更新，窗口固定
     160 行；顺手修正 takeLast(300) 取到最旧日志的语义错误（requestLog 是 newest-first）。
  5. 所有定时刷新的标签赋值走 setTextIfChanged / setValue / setForegroundIfChanged，
     消除「新旧值相同也 firePropertyChange → 重绘」的空赋值风暴。
  6. KButton 在 paintComponent 内只在颜色变化时 setForeground（原先每帧无条件赋值，
     等于在绘制期间请求重绘）。补禁用态视觉（弱底色 + 弱文字）。
  7. 托盘菜单的指针轮询 Timer 从常驻 10Hz 改为「菜单显示时才跑」。

五、刷新额度
  1. 去掉失败时的模态弹窗（showKMessage 是模态 SunAwtDialog，会把 EDT 整体阻塞——
     这是「点刷新额度界面就卡死」的直接原因）。改为按钮就地回显
     「刷新中 x/y」→「已刷新 N 个账号，M 个失败」。
  2. 并发度 3 → 2 降低上游风控命中；按钮在刷新期间置灰禁用，防连点叠请求。
  3. 账号表余额列拿不到值时带原因（凭证失效 / Connection reset / 上游无解析额度 /
     未同步），不再是一个无从判断的「—」。

实测（安装版 0.7.0）：全量额度刷新 11 账号 ≈4.8s（并行 2）；trae 3 账号中 1 个 2400 正常、
1 个凭证失效、1 个上游无可解析额度；codebuddy 3 个、raccoon 3 个均正常；loomy 2 个
Connection reset（域名被当前网络整段封锁，与代码无关）。空闲 CPU 由约 4% 降至 3% 左右，
日志页/表格/悬停路径的无效重绘已移除。

六·i  0.8.0 —— WebView2 版壳（彻底替换 Swing 界面）

一、为什么要换
  旧版是「Swing 自绘无边框窗口」：整窗覆一个 glassPane 截获所有鼠标事件，
  自己做命中测试、自己合成 ENTERED/EXITED/CLICKED、自己算拖动坐标、
  自己调 SetWindowPos。这套设计带来四层代价，前面几轮只修掉了其中三层：
    1) 每个鼠标移动都要遍历组件树做命中测试（窗口大、DPI 高时尤其贵）
    2) 拖动时每帧同步改窗 + 整窗重排
    3) 定时刷新与鼠标事件同抢 EDT
    4) Windows 原生行为（Aero Snap / 贴边 / 高 DPI 字体缩放）全部缺失，只能自己仿
  0.7.0 把 1~3 修了，但第 4 层是架构性的：只要自己画窗口，就永远在跟系统对着干。
  WebView2 版把「窗口」和「界面」两件事分别交还给 Windows 与 Chromium，这四层全部消失。

二、新架构（三模块）
  :core    不变。同一份 Kotlin 网关引擎，与 Android 端共用。
  :desktop 保留（旧 Swing 壳仍可用，作为回退；数据格式完全一致）。
  :server  新增。复用 core + desktop 的加密存储与 AutoRouteManager，
           对外提供 /ui/… 管理 API 与静态前端。**端口 8792，与网关 8790 分开**，
           客户端接入地址不受换壳影响。
  shell/   C# WebView2 外壳（AiGatewayWeb.exe）。只做三件事：
           拉起后端子进程、开窗口、把窗口按钮点击转成原生操作。

三、窗口交互（这一版花了最多时间，结论值得记下来）

  **唯一可行架构：标题栏必须是 Form 的子控件，不能是 HTML。**
  原因：WebView2 的子窗口铺满它自己的边界，凡是它覆盖到的像素，鼠标消息全部进
  Chromium 进程，**父窗口的 WM_NCHITTEST 永远不会被调用**。换句话说，
  只要标题栏画在 HTML 里，无论 NCHITTEST 怎么写、CSS 怎么设 app-region，
  拖动都不可能生效。（本版前三次尝试分别栽在 NCHITTEST、CSS app-region、
  IsNonClientRegionSupportEnabled，全是这一个根因。）

  最终布局：
    Form.Padding = 8                → 四周 8px 环是 Form 自己的客户区 ⇒ 边缘缩放生效
    TitleBarPanel (Dock=Top, 63px)  → Form 的普通子控件 ⇒ 鼠标消息进 Form 的消息循环
    WebView2 (Dock=Fill)            → 只占下面那块，不再吃掉标题栏像素

  三处关键实现：
  1) Dock 顺序必须「先加 Fill、后加 Top」。WinForms 的 Dock 布局从 Controls 末尾
     向前处理；反了 Fill 会先占满客户区，Top 布局时就已无空间，标题栏高度变 0
     （表现：标题栏看不见、点不到、拖不动）。实测日志确认了这一点。
  2) WM_NCHITTEST（`ShellWindow.DecideHit`）：
       边缘 8px（DPI ×1.5 折算）→ HTLEFT/HTRIGHT/…，四角优先
       标题栏带且不在按钮矩形内 → **HTCAPTION** ⇒ DefWindowProc 进入系统模态移动循环
       窗口按钮矩形内 → HTCLIENT（交给 TitleBarPanel 自己处理）
     坐标取自 **lParam**，不是 Cursor.Position：系统在贴边吸附/DPI 切换/键盘触发时
     也会发本消息，那时真实光标与待测点无关。
  3) TitleBarPanel.OnMouseDown 里再显式 `ReleaseCapture()` +
     `WM_NCLBUTTONDOWN(HTCAPTION)` 作为主路径；同时在 OnMouseMove 里留了一条
     「系统循环未接管就自己挪窗口」的兜底（远程桌面等环境用得上）。

  判定表抽成纯函数并配 `--selftest`，**12/12 通过**（含标题栏 HTCAPTION、
  按钮区 HTCLIENT、四边四角、最大化态底边不误触发）。

  **验证边界（必须说清）**：本机这台测试环境没有交互式桌面
  （`GetForegroundWindow()=0`、光标坐标恒为 0,0），Robot 与任何真实鼠标注入
  都不产生事件，`WindowFromPoint` 仍能命中窗口但消息不会走正常路由。
  因此「拖动是否真的跟手」这一项**只能在你的真实桌面上验证**，我这边只验证到
  判定表正确 + 布局正确（日志：titlebar bounds={X=8,Y=8,W=1224,H=42}、
  webview bounds={X=8,Y=50,W=1224,H=762}）。

四、前端
  纯 HTML + CSS + 手写 JS，无构建步骤、无第三方依赖（离线可用）。
  颜色全部走既有 kd-design-system.css 的令牌，深浅主题只切 data-kd-theme。
  九个页面全部实现：概览 / 运行日志 / 供应商 / 账号 / 模型目录 /
  智能路由 / 网关设置 / 客户端密钥 / 调用记录。
  概览四张卡两两并排：实时拓扑（贝塞尔扇出 + 在途光斑）、上下文容量分布、
  消耗趋势（近 14 天双折线）、最近调用。

  布局坑（两次都是同一类问题）
  - `GridLayout` / `auto-fit minmax(300px)` 在小屏退化：本机 150% 缩放，
    1280×800 物理屏的逻辑工作区只有 853×533，内容区仅 ~543 CSS px，
    300×2+12=612 放不下 → 自动变单列。下限改 240px 并用 `min(240px, 100%)`。
  - grid item 的 automatic minimum size = min-content，而 canvas 的 min-content
    等于它的 width 属性（上千像素），一列就被撑满。`.split2 > * { min-width:0;
    overflow:hidden }` 才能真并排。
  - `hidden` 属性被 `display:grid` 覆盖（前者只是低优先级样式），
    弹窗遮罩会一直显示。必须补 `.modal-mask[hidden]{display:none}`。

五、数据与迁移
  发布版与旧版共用 `%APPDATA%\AIGateway\data`：账号、额度、路由组、调用记录、
  master.key 全部沿用，**换壳不需要重新登录任何供应商**。
  验证：发布版起来后 /ui/state 返回 11 个账号、额度 31968、模型 85 个。

六、构建
  build-web.ps1 产出 build\release-web\（约 51 MB）：
    AI Gateway.exe                     启动器（WebView2 外壳）
    Microsoft.Web.WebView2.*.dll       **必须与 exe 同目录**（程序集解析只看应用目录）
    WebView2Loader.dll                 同上（托管包装按相对路径加载它）
    runtime\                           裁剪后的 JRE（保留 java.desktop，签到调度用 Swing Timer）
    app\                               后端 jar（core/desktop/server + 依赖）
    web\                               前端静态文件
  脚本用 PowerShell 而不是 .bat：安装路径含空格（"AI Gateway"），
  cmd 的 xcopy/copy 在这种路径下会静默把参数拆成两个。
  另：`.bat` 必须保持纯 ASCII —— cmd 按 OEM 代码页读 .bat，
  UTF-8 中文注释会被拆成非法命令（本项目已踩两次）。

七、已知限制
  - WebView2 Runtime 需存在（Win10/11 通常自带；缺失时外壳会弹提示，
    可从微软官网装 Evergreen Runtime）。
  - 旧 Swing 版未删除，仍是可回退的入口；两者共用数据目录，
    不要同时运行（单实例锁端口 8791 会挡住第二个）。

六·j  0.8.1 —— 标题栏拖动修复（本轮唯一改动）

问题：0.8.0 装上去后「窗口无法移动」。

根因（一句话）：**WebView2 的子窗口铺满它自己的边界，凡是被它覆盖的像素，
鼠标消息全部进 Chromium 进程，父窗口（Form）的 WM_NCHITTEST 永远不会被调用。**
所以只要标题栏画在 HTML 里，拖动就永远不可能生效——与 NCHITTEST 写得对不对无关。

三次失败尝试与各自的真实死因：
  1) WM_NCHITTEST 查表 + HTML CSS app-region：NCHITTEST 收不到消息（被子窗口吃掉）
  2) CSS app-region + IsNonClientRegionSupportEnabled=true：CSS 侧确实算出 drag，
     但窗口不动（该开关在当前 WebView2 Runtime 未接管拖动，且它同样要求
     app-region 区域不在子窗口的滚动内容里）
  3) JS 按下 → postMessage → C# 里 ReleaseCapture + WM_NCLBUTTONDOWN：
     消息链打通了（日志可见），但 HTML 标题栏仍在顶部占 42px，
     点击落点被 HTML 元素吃掉，C# 标题栏被压在下面收不到事件

最终方案（结构与代码都改）：
  · **删掉 HTML 的 <header class="titlebar">**（index.html / app.css / app.js 全部清掉）
  · 标题栏改为 C# 的 TitleBarPanel（Dock=Top，63px @150%），它是 Form 的普通子控件，
    鼠标消息直接进 Form 的消息循环
  · WebView2 用 Dock=Fill 只占下面那块，顶部那 63px 不再被它覆盖
  · Form.Padding=8：四周 8px 环仍由 Form 负责 ⇒ 边缘缩放在 WebView2 之外也能用
  · WM_NCHITTEST：边缘→HTLEFT/…、标题栏空白区→**HTCAPTION**（系统模态移动循环）、
    按钮区→HTCLIENT（交 TitleBarPanel 自己处理）

  修改文件：shell/TitleBar.cs（新增，376 行：自绘标题栏 + 四个按钮 + 拖动发起）、
           shell/Program.cs（布局改 Dock 结构 + TitleBarPixelHeight/ButtonLeftPixel）、
           web/dist/index.html（删 header）、web/dist/app.css（删 .titlebar 规则）、
           web/dist/app.js（删窗口按钮绑定，主题切换改由 C# 调 window.aigwToggleTheme）

另外修掉的两个通用缺陷（影响所有调试/打包，不只拖动）：
  · 命令行参数循环上界写成 `args.Length - 1`，会漏掉最后一个参数 ——
    `--dragtest` 这类「无值开关」永远解析不到（表现为「钩子加了但日志没动静」）
  · WinForms 的 Dock 布局从 Controls 末尾向前处理，必须「先加 Fill、后加 Top」。
    反了 Fill 先占满客户区，Top 布局时已无空间，标题栏高度变 0（看不见点不到）。
    实测日志 `[layout] titlebar bounds` 已确认正确值 = {X=8,Y=8,W=1224,H=42}

验证：
  · `--selftest` 判定表 **12/12 PASS**（四边四角缩放、标题栏 HTCAPTION、按钮区 HTCLIENT、
    内容区 HTCLIENT、最大化态底边不误触发）
  · 布局日志：titlebar bounds={X=8,Y=8,Width=1224,Height=42}、webview bounds={X=8,Y=50,...}
  · 九页全渲染、无 JS 错误；发布版端到端拉起后端，返回 11 账号 / 31968 额度 / 85 模型
  · **真实拖动未能在本机验证**：这台测试环境没有交互式桌面
    （GetForegroundWindow()=0、光标恒为 0,0），Robot 与任何鼠标注入都不产生事件。
    需要在你的真实桌面点一下验证；若仍不可拖，<dataDir>\shell-launcher.log 会记录
    `[titlebar] MouseDown` 与 `[drag] BeginNativeDrag called`，
    两者都出现仍不移动 ⇒ 系统循环未接管（可改用兜底路径，见代码注释）。

产物：build\release-web\（52 MB）。旧 Swing 版 path 保留可回退。

六·k  0.9.0 —— 把 core 的「策略与媒体」能力接进界面
======================================================================

## 一、这轮在补什么

`MEMORY.md` 里的长期待办是「上游 core 能力在桌面 UI 尚未暴露」。逐项核对后，
真正「core 已完整实现、界面零入口」的有两组：

  1. 账号选择策略 + 故障转移参数 + 并发闸门 + 模型级冷却 + 会话亲和
     core 里 5 种 AccountStrategy（SMART / ORDER / ROTATE / USAGE / PACE）、
     重试退避、两级熔断、并发上限、模型冷却全部可配置，但只能手改
     secure/settings/failover.json 才生效——界面上连一个开关都没有。
  2. 媒体端点 POST /v1/images/generations、/v1/audio/transcriptions
     core 早已实现（含选号/换号/CLIENT 错误直返/调用记录），界面侧完全没有入口，
     等于要验证一次出图必须自己写 curl。

本轮新增两个页面把这 11 项全部接上。

## 二、高级策略页（/ui/strategy）

新增端点：
  GET  /ui/strategy        读快照（failover + 亲和条数 + 熔断现状 + 冷却现状）
  POST /ui/strategy/save   写回（只覆盖显式给出的字段）
  POST /ui/affinity/clear  清空会话亲和表
  POST /ui/cooling/clear   解除全部模型级冷却

界面分三张卡：
  账号选择策略   策略下拉（5 档，每档带「什么时候该用」的一句话）+ 报错账号冷却毫秒 + 故障转移总开关
  故障转移参数   重试 5 项、熔断 3 项、并发 3 项、模型冷却 2 项，共 13 个数值输入
  运行现状       会话亲和条数 + 熔断中的供应商 + 冷却中的模型（各带一键清除）

范围校验与 core 完全一致：策略名走 `AccountStrategy.valueOf`，未知值直接
返回 `{ok:false,message:"未知账号策略：X"}` 而不是静默落回 SMART；
数值裁剪复用 `ConcurrencyConfig.clampMaxPerAccount / clampMaxGlobal /
clampQueueTimeoutMs`，其余按 core 的 fromJson 上下界裁剪。

**两个刻意的设计决定**
  · `routes`（模型级故障转移映射）不随快照下发，保存时从当前配置原样带过去。
    它可能几百条，2 秒一拍白传；且它不出现在界面上，一保存就清空是事故。
  · 「运行现状」单独抽成 paintStrategyStatus()，只重画那一块。
    整页每 2 秒重画会把用户正在输入的数值打回原值——旧 Swing 版栽过同类问题，
    这版不让它重演（loadState 里用 activeElement 判 INPUT/TEXTAREA 跳过重建）。

## 三、媒体实测页（/ui/media）

新增端点：
  POST /ui/media/image       出图
  POST /ui/media/transcribe  转写

**不走第二套实现**：两个端点都是把请求重建后转发到本机网关
`POST /v1/images/generations` / `/v1/audio/transcriptions`，于是选号、换号、
冷却、熔断、CLIENT 错误直返、调用记录全部与客户端实际路径完全一致。
界面上看到的结果就是客户端会拿到的结果，不会出现「界面能出图、客户端报错」。

  · 出图：网关只给 base64（上游不给外链），后端把它转成 data URL 直接喂 <img>，
    省一次二次请求。响应里的 dataUrl / bytes / elapsedMs 都是实测值。
  · 转写：WebView2 拿不到真实文件路径，前端 FileReader 读成 base64 上传，
    后端重建 multipart（含 Content-Type 与 boundary）再转发。
    这条路在上游真实跑通了：用一段 16kHz/2s 的合成 WAV 打 loomy，
    返回「该账号的模型目录里没有声明音频输入的模型，无法用对话通道转写」——
    是上游原话，不是占位文本，证明 multipart 重建与鉴权链路正确。
  · 能力提示：页面上直接写「图像供应商：无（会返回 400）」/「转写供应商：Loomy」，
    数据来自快照里新增的 providers[].image / providers[].audio 两个布尔字段
    （由 `Provider.supportsImageGeneration / supportsAudioTranscription` 直接读，
    不从 capabilities 字符串里二次解析，避免枚举改名后静默失效）。

## 四、验证（全部实测，无 mock）

  · `:server:compileKotlin` 通过；`build-web.ps1` 出 51.4 MB 包。
  · 策略保存往返：写 PACE / 4 次重试 / 250→2500 退避 / 单账号 2 / 全局 12 /
    冷却 300s，返回体逐字段一致；重启进程后再读仍是同一组值（落盘生效）。
  · 错误路径：`accountStrategy="BOGUS"` → `{ok:false,"未知账号策略：BOGUS"}`，且不写坏配置。
  · 快照变化：端到端 `model="auto"` 流式 chat 前亲和表 0 条，chat 成功后变 1 条
    （证明亲和绑定真的发生在真实调用里），点清空后回 0。
  · 图像端点：无可用图像供应商时返回 `{ok:false,"没有支持图片生成的供应商可用…",elapsedMs:8}`。
  · 转写端点：空 body → `缺少文件内容`；真实 WAV → 上游真实拒绝原因（见上）。
  · 外壳命中判定自测 **12/12 PASS**（改动未碰窗口层，回归确认）。
  · 全 11 页渲染巡检（go(page) + 数卡片/节点）：strategy 首次停在「加载中」是
    真 bug——快照靠 `loadState` 的分支拉取，首次进页面时还没值。
    改为启动时预取 `loadStrategy()`，复查后 strategy=3 卡/95 节点正常。

## 五、已知限制

  · 图像端点在这台机器上无法出真图：6 家里只有 antigravity 声明图像能力，
    而它 0 个账号。要真出图得先登一个 antigravity 账号——界面已把这个状态
    直接写在页面上，不会再让人点一次才看到 400。
  · 转写同理：只有自定义供应商声明该能力，内置 6 家全不支持；loomy 虽标
    aud=True 但上游明确回「模型目录里没有音频输入的模型」。
    也就是说这条路径**当前在这台机器上不可用**，端点与错误传播是正确的，
    缺的是有该能力的上游账号。
  · 策略页每 2 秒会重新读一次快照；只在输入框失焦时才重画「运行现状」，
    数值输入框本身永不自动重建。

产物：build\release-web\（51.4 MB）。APP_VERSION 0.8.0 → 0.9.0。

六·m  0.9.2 —— 多实例隔离（数据目录 + 锁 + 端口派生）
==============================================================================

上一轮遗留的「Swing 版与 WebView2 版共用数据目录，不可同时运行」只是表面现象。
真正的限制在**实例身份定义**上：旧实现把「一个实例」绑在三个固定端口上——
8791（单实例锁）、8792（管理面）、8790（网关）。于是任何「换数据目录跑第二个
实例」的尝试都在第一步就死掉，哪怕两份数据完全不共享。

实际代价是每次验证都得先杀掉正式实例、验证完再拉回来；两个目录的数据本来
互不可见，进程却互相排斥。这一轮把它拆开。

一、锁改成「数据目录下的文件锁」
  · 旧：`ServerSocket(8791)`，进程级、与目录无关 → 第二个实例必被拒。
  · 新：`<dataDir>/.instance.lock` 上的 `FileLock`。同一目录第二个进程仍被拒
    （这是必须保留的，两个进程写同一份加密存储会坏数据），不同目录互不影响。
  · 默认数据目录额外保留 8791 的监听：Swing 版还在仓库里、随时可能回退运行，
    它只认那个端口、不认识文件锁。只有默认目录两边都会用到，所以只在那里占住。
  · 锁句柄全程持有，进程退出（含崩溃）由系统释放；另注册 shutdownHook 显式释放，
    避免「上次没退干净，下次打不开」。

二、端口按目录派生，写回文件给外壳
  · 默认目录：UI 8792、网关 8790 —— 老用户升级后行为**零变化**。
  · 派生目录：从路径的 SHA-256 落到 18100+seed×2，UI 与网关各占相邻一个号；
    真被占用时依次往后探到空位（实测 A→18164/18165、B→18128/18129）。
  · 结果写进 `<dataDir>/.instance.json`（Properties；先写 .tmp 再原子替换）。
    外壳是独立进程，这是两边唯一都能可靠读到的通道。
  · 开关 `--port` 仍可显式覆盖 UI 端口，写文件时会写**实际监听值**而不是派生值
    （这一点最初写错了：`--port 18501` 时文件里仍是 18164，外壳必然连错）。

三、外壳不再硬编码 8792
  · 启动顺序：`--port` > `.instance.json` > 默认 8792。
  · **存活判定必须带数据目录**（`IsUiAliveFor`）：原来只看「8792 上有没有 HTTP」，
    第二个实例会把主实例的后端误认成自己的，于是不启动自己的后端、窗口连到
    别人家的数据上。这是本轮最隐蔽的一处，只有真正并行启动才会暴露。
  · 端口文件可能是上一轮残留：拉起后端前先删，再按新写出的文件跟。
  · 等待循环每轮重读端口文件——后端算出的端口可能和上次不同。

四、侧栏两处真实的布局缺陷（顺路修掉）
  · `renderStatus()` 在 `#statusPill` 上**第一行就抛 TypeError**：侧栏换成 WebView2
    时这个节点被删了，但代码还在更新它。异常落在心跳的 try 里，看不出来，
    后果是它后面所有更新——状态灯、接入地址、派生标记——**从来没有执行过**。
    接入地址一直停在「—」的原因就是这个，跟本轮改动无关，是旧 bug。
    修法：所有节点访问走判空（`setIf`），缺失的装饰节点不阻断关键更新。
  · 侧栏单列滚动把底部推出可视区：实测内容 593px / 可视 508px，
    「客户端接入地址」排在 585px 处，**不滚根本看不到**。
    拆成「导航区滚动 + 底部固定」，并把导航项内边距 8→5px、分组间距收紧，
    11 项全部落在 435px 内、无需滚动。
  · 地址本身 161px 宽而可用只有 143px：省略号正好切掉端口——而端口是派生实例
    唯一有用的信息。改两行显示（host:port 换行到 /v1），不再截断。

五、界面标明实例身份
  · 快照新增 `derived` / `uiPort`。
  · 派生实例侧栏底部显示橙色「派生实例 · <目录名>」，tooltip 带完整路径与两个端口。
    默认目录不显示——单实例用户不该看到多一行噪音。

验证（全部真实进程，非 mock）
  · 同一目录二次启动 → 被拒（「数据目录已被另一个实例占用」）。
  · **主实例 8792 全程不杀**，并行拉起派生目录实例：两份进程、两套端口、

  · 外壳 `--selftest` 12/12 PASS；11 页逐页截图全部正常。

十三、0.9.3：全流程实测 + 代码规范化（本轮）
======================================================================

这一轮做的是「把整个程序自己走一遍，再把写随意的部分整理干净」。
所有结论都来自真实进程：真后端 + 真 Chromium（headless CDP）+ 真壳（WebView2）。

一、全端点数了 57 个请求（.tmp/uitest/api_probe.py）
  · 覆盖全部 31 个端点，含读接口、写接口、参数缺失、非法参数、不存在的资源、
    GET 打写接口、畸形 JSON、超大请求体。
  · 结果：**0 个 500**。参数错误一律 400、未知接口 404、超大请求 413。

二、11 个页面逐页点完每一个按钮（.tmp/uitest/ui_walk.js）
  真 Chromium 打开页面，按「页头动作 → 卡片按钮 → 开关 → 日志过滤 → 表格行」
  顺序逐个 click，每个按钮后判断弹窗/Toast，再关掉弹窗继续下一个。
  · 概览 4、运行日志 7(tab)、供应商 7、账号 46、模型目录 1、智能路由 94、
    网关设置 7+5 开关、客户端密钥 1、调用记录 1、高级策略 3+1 开关、媒体实测 2。
  · 最终：**运行时异常 0、console.error 0、横向溢出 0**。
  · 空数据目录（全新安装）同样跑一遍：11 页全通，首次引导三步条正常出现。

三、压力与边界（.tmp/uitest/stress.py）
  · keep-alive 复用同一连接 60 轮 × 5 个请求（模拟连刷页面）→ 全部 200。
    这一条专门盯「偶发 400 BAD REQUEST」：原因是静态资源走 chunked，
    连接复用时残留字节被下一个请求当成新的请求行。改成固定长度后消失。
  · 10 线程 × 20 次并发写 → 200 次全部成功、状态一致（写操作串行锁生效）。
  · 41 MB 请求体 → 413 且服务存活；畸形 JSON / Content-Length 不符 / PUT / 路径穿越
    → 分别 200(ok:false) / 400 / 400 / 404，服务均不崩。

四、真实壳端到端
  · 发布目录启动 `AI Gateway.exe` → 自动拉 javaw → `/ui/state` 200。
  · 布局日志：`titlebar={8,8,1224,42}`、`webview={8,50,1224,762}`，标题栏可点可拖。
  · `--selftest`：命中判定 12/12 PASS（含最大化态底边不缩放、按钮区不拖窗）。

五、修掉的真问题（不是重构，是 bug）

  1. **主界面卡的根因找到了：模型数每 2 秒打一次全供应商上游。**
     心跳调 `/ui/state` → `cachedExposedModels()`。这个名字像纯读缓存，
     实际内部走 `modelsStreaming{}`，会给每个供应商提交一次拉取任务再聚合：
     实测单次 300–350ms，冷启动第一次 2.4 秒。
     心跳 2 秒一拍 = 每两秒一次全供应商聚合，EDT/页面线程全被拖住——
     这就是「拖动卡、点一下要等」的真正来源，不是渲染。
     修法：管理面自己维护一份模型数快照，后台线程按节奏刷新
     （有内容 5 分钟一次；刚启动 10 秒一次最多 5 次；确认没目录后退到 20 分钟），
     心跳只读字段。实测 `/ui/state` 从 340ms 降到 **9ms**。
     顺带修正口径：路由组投影（`group/auto`）不再算进「模型数」——
     否则「一个模型都没拉」会显示成「1 个」，用户会去模型页找一个不存在的模型。

  2. **写端点不再接受 GET。**
     原来对方法一视同仁，于是 `GET /ui/account/delete?providerId=x&uid=y`
     真能删账号——浏览器里任意页面都能构造这个 GET（CSRF 面）。
     现在写端点一律只认 POST，其余 400 并说明原因。

  3. **签到定时器从 `javax.swing.Timer` 换成 `ScheduledExecutorService`。**
     服务端进程没有 Swing 事件循环，原来那版是靠 Timer 的守护线程勉强跑起来的，
     打包时还得额外保留 java.desktop 模块。纯 Java 定时器不依赖 EDT。

  4. **答复 500 的三处去掉。** 未知供应商、请求体读超时、body 读异常——
     原来都落进兜底 catch 变成 500，浏览器控制台一条红字，排查时容易误判成后端挂了。
     现在分别是 400 / 400 / 400，且 500 会额外写一条 `[aigw-ui]` 日志（不再只在界面闪一下）。

  5. **NanoHTTPD 自带日志关掉。** 它把「客户端在响应写完前断开」记成 SEVERE 并打完整栈，
     而那是完全正常的事（刷新页面、关窗口、点取消）。日志里一堆
     `SocketException: 你的主机中的软件中止了一个已建立的连接` 只会淹没真故障。

  6. **favicon 404 消除。** 内联 SVG data URI，控制台不再每次多一条红字。

  7. **前端补三条健壮性**
     · `api.get/post` 统一封装：超时（state 8s / 写 15s / 额度 180s）、
       非 200 与非 JSON 一律归一成 `{ok:false,message}`。原来每处各写 try/catch，
       漏一处就是 `Unhandled (in promise) SyntaxError: Unexpected token 'B'`
       ——这正是本轮第一次巡检抓到的唯一运行时异常。
     · 窗口隐藏时停心跳（`visibilitychange`），回前台立刻补一次；
       原来最小化后仍在每 2 秒发一次请求。
     · 全局 `error` / `unhandledrejection` 兜底：桌面应用没有「默认开着 DevTools」
       这回事，异常只落 console 等于消失。现在弹 Toast（10 秒内同一条只弹一次，防刷屏）。
     · 音频转写在**前端先卡 30MB**：base64 会放大 4/3，服务端上限 40MB。
       不拦的话要等几十秒上传完才收到 413，用户只会觉得「点了没反应」。
     · 剪贴板复制加降级路径：WebView2 默认不弹 clipboard 权限框、直接 reject，
       现在退回 `execCommand('copy')` + 隐藏 textarea。

七、本轮实测抓出的一处回归（已修）

  **冷启动（全新数据目录）时外壳等满 90 秒超时，窗口一个都不出。**

  这是本轮重构引入的：原来 `followPortFile` 的判据是「端口文件是否存在」，

  全新目录第一次启动时文件还不存在，此时仍必须跟随后端写出的新文件。

  暴露方式：用全新目录直接启动发布版 exe，`shell-launcher.log` 里只有
  `launch javaw -> True` 就没了，18 秒后进程还在、窗口不出。

  把「后端自己退了」与「等不到」分成两种提示——前者去查配置与日志，
  后者多半是端口被占，混成一句「超时」会给出错误的排查方向。

  验证：全新目录 3 秒出窗（`[wait] 后端端口 -> 18222`）；
  已有目录带旧端口文件同样 3 秒出窗（`[wait] 后端端口 -> 18138`）。

  按「不跟随」处理，外壳会一直盯默认 8792，而后端按目录哈希派生的端口是 18xxx，
  于是必然等到超时。

  它只有在「真跑发布版 exe + 全新目录」时才会暴露：单进程测后端永远是通的，
  用已有目录测也永远是通的（那里有上一次留下的端口文件）。
  这是本轮唯一由我自己的改动造成的故障，也是唯一一条靠"看代码"发现不了的。

  修法：判据改回「没显式给端口就跟文件」，默认值只作为等待期间的起点；
  并把 `WaitReady` 改成三态（Ready / Exited / Timeout），
  让「后端自己退了」与「等不到」给出不同提示——前者要查配置与日志，
  后者多半是端口被占，混成一句「超时」会把排查方向带偏。

  验证：全新目录 3 秒出窗（`[wait] 后端端口 -> 18222`）；
  已有目录带残留端口文件同样 3 秒出窗（`[wait] 后端端口 -> 18138`）。

七、本轮抓出并修掉的两处回归 + 一处健壮性缺陷（都是我自己改出来的）

  ① **全新数据目录冷启动 → 等满 90 秒超时，窗口一个都不出。**
     端口跟随的判据从「端口文件是否存在」错写成「是否显式给了 --port」。
     但这两者不是一回事：全新目录第一次启动时文件还不存在，此时
     **仍然必须跟随后端写出的新文件**。按「不跟随」处理，外壳会一直盯
     默认 8792，而后端按目录哈希派生的端口是 18xxx，必然等到超时。
     只有「真跑发布版 exe + 全新目录」才暴露：单跑后端永远通，
     用已有目录测也永远通（那里有上次留下的端口文件）。

  ② **`--port` 完全失效。** 拆文件时把 `UiPort = opts.Port` 那一行丢了，
     走进 `else` 分支后端口仍是 0。表现是 `--port 18138` 不生效、
     外壳去连 8792 然后报「后端启动即退出」——**参数无效比崩溃更难查**，
     因为日志里只有一句"退出了"，看不出是端口压根没被采纳。
     修法：显式端口必须赋值并跳过文件读取，同时落一行 `[args] 使用显式端口 N`。

  ③ **启动失败会永久挂死（最隐蔽的一条）。** `MessageBox.Show` 是模态的，
     在没有交互桌面的环境里（CI、远程会话、本机这种 `GetForegroundWindow()==0`
     的机器）它永远等不到人来点。批量截图时 8 个进程全部卡在同一个
     隐形的错误框上，**15 分钟没有任何输出**，只在任务管理器里占着。
     修法：加 `Headless` 概念（给了任何诊断参数即判定为自动化运行），
     失败时写日志 + 返回退出码（3=后端起不来，4=窗口崩，5=WebView2 初始化失败），
     绝不弹框。另外「后端刚启动就退出」加一次 1.5 秒重试——
     那通常是上一实例还在收尾、文件锁没放开。

  验证（修完之后）：
    · 全新目录 3 秒出窗（`[wait] 后端端口 -> 18222`）
    · 已有目录带残留端口文件 3 秒出窗（`[wait] 后端端口 -> 18138`）
    · 同目录重复启动 + 诊断模式 → 9 秒内以退出码 3 结束，日志写明三重原因
    · `--port 18138` 生效（`[args] 使用显式端口 18138`），11 页截图 11/11 成功

十四、0.9.4：路由组（core 最后一块「零 UI 入口」的能力）
======================================================================

这一轮补的是界面上**完全没有入口**的一组能力：core 的 `RoutingGroup`。
0.9.0 已把账号策略与媒体端点接上，路由组一直没接——服务端只有
`POST /ui/groups` 一个整表覆盖端点，前端从未调用过它。结果是：

  · 除智能路由页维护的 `auto` 组之外，无法自建任何组；
  · 组的 `strategy`（ORDER / WEIGHT）无法改；
  · 7 类分流规则（token 阈值 / 图片 / 压缩请求 / 工作目录 / 时段 / 星期）无法配；
  · 成员 priority 与 weight 只能手改 `settings/routing_groups.json`。

新增第 12 页「路由组」，把上述全部接上。

一、服务端（`UiRoutes.kt`，+180 行）

  · `GET /ui/groups`：全部组 + 每组的**可解析性**判定。
    `usableMembers` 只统计「供应商已注册 + 未禁用 + 有可用账号」的成员——
    网关自己不管这个（组里挂失效成员时它自动跳下一个候选），但界面上
    必须能看出「这条候选现在选不到号」，否则用户会以为规则没生效。
  · `POST /ui/groups/save`：**单组**新增/覆盖。
    与既有的整表端点 `POST /ui/groups` 的区别是不碰别的组：路由组页与
    智能路由页改的是同一个文件，整表回写会让另一页未刷新时的旧值把
    对方的改动画回去（实测：在路由组页保存一次，auto 组候选链被覆盖成旧值）。
  · `POST /ui/groups/delete`：删单组，不存在时 `ok:false` 而不是 404。
  · `/ui/groups` 本身改成「GET 读 / POST 写」双用，与其它端点保持一致。

二、前端（`web/dist`，第 12 页，约 520 行）

  · 列表：组名 / 策略 / 成员数 / 规则数 / 状态 / 操作。状态列显示
    `可用成员数/成员数`，四种状态各自可辨（停用 / 无成员 / 全部失效 / ok）。
  · 编辑区三张卡：组信息（组名、显示名、策略、启停）、成员、规则。
  · 成员：从**真实模型目录**挑选（未拉取时先说「正在拉取」再拉），
    支持上移/下移/删除，priority 与 weight 各一个窄输入。
  · 规则：7 类条件全在弹窗里（token 阈值、图片、压缩请求、工作目录、
    时段、星期、目标成员）。时段输入 `HH:MM-HH:MM`，跨午夜（22:00-02:00）可填。
  · `auto` 组只读：成员由智能路由页按目录生成与清理，这里给编辑入口

三、实现中修掉的一个真 bug（走完整流程才暴露）

  **填了组名 → 加个成员 → 组名没了 → 保存报「组名不能为空」。**

  原因：本页会重建整块编辑区（加成员、加规则、成员排序都走 `renderPage`），
  重建时输入框回显的是草稿里的 `g.id` / `g.name`。原先输入只留在 DOM 里、
  没写回草稿，于是任何一次重建都会把刚输入的组名清空。

  这条用「看一眼界面」发现不了：填完名字直接点保存是通的，
  只有在中间插入一次重建才复现——正是深度巡检脚本（见下）抓出来的。

  修法：`input` 事件即写回草稿并标脏；组名同时就地更新「对外 id」那行文本
  （就地改而不重绘，否则每敲一个字都会抢光标）。

十六、0.9.5：修「服务出错了，请稍后重试 / 4001」
======================================================================

用户实测：客户端调网关，界面连着回
    服务出错了，请稍后重试
    We're sorry, the param is invalid. Please try with a valid param. 4001

一、根因（从生产数据的调用记录里查出来的，不是猜的）

  记录里 4 条 FAILED，全部是 `trae / Auto`，error 字段逐字就是上面那句，
  上游原文是 `{"error":{"code":4001,..."type":"CLIENT"}}`，请求体里写着
  `{"model":"Auto", ...}`——**首字母大写**。

  而路由组的组名是 `auto`（小写）。`RoutingGroupSettings.find(id)` 用的是
  `it.id == id` 精确比较，于是 `"Auto"` 没被认成组引用；
  接着走到「无前缀 → 无条件兜底」，把 `Auto` 当普通模型名塞给了 trae 的某个账号，
  上游当然不认识这个模型，回 4001 并带一句泛化文案。

  也就是说：**这不是上游的错，是我们把不存在的模型名放过去了。**
  用户看到的「服务出错了」完全是上游的通用措辞，真正的原因（模型名不存在）
  被两层掩盖：一层是我们没拦住，一层是上游不会说清。

  为什么客户端会发大写的 `Auto`：部分客户端（Claude Code 一类）会把模型名
  规范成标题大小写后再发。同一批记录里还有 `trae/trae-auto` 也报 4001——
  那条前缀被正确识别成 trae，但 `trae-auto` 这个子模型不存在，同样被原样透传。

二、修了四处（三处行为 + 一处文案）

  1. **组名匹配忽略大小写**（`RoutingGroups.find` / `groupIdOf`）
     精确优先、不区分大小写兜底：`auto` / `Auto` / `AUTO` / `group/Auto` /
     `GROUP/AUTO` 全部认作同一个组。同时补了 `findAny()`（不过滤 enabled），
     给界面「读停用中的组」用。
     没有直接改成 equalsIgnoreCase：组 id 由用户自己命名，万一真有两个只差
     大小写的组，精确匹配仍优先。

  2. **目录里不存在的模型名 → 明确拒绝，不再兜底透传**（resolveRoute）
     判据是 `lastGoodCatalog` 快照（**只读字段，不触发上游聚合**，因为这里在
     路由解析热路径上）。四种情形不拦，避免误杀：
       · 目录为空（还没拉过）——无从判断
       · 该供应商在目录里一条都没有（未登录 / 没拉到）——同上
       · custom 供应商——模型名由用户自定义，认不认由上游答
       · 子模型确实在目录里（忽略大小写 + 归一化）——放行
     另一个入口分支也补了：`trae/trae-auto` 这种「前缀对、子模型不存在」同样拒绝。

  3. **报错文案分三种**（`missingModelMessage`）
     原先「没写 model」与「写了但不存在」共用一句「缺少 model 参数」——
     用户明明写了，被告知没写，只能去翻客户端配置。现在：
       · 空 → 缺少 model 参数

六·P  0.9.9 追加 —— 备份与恢复（侧栏第 13 项）
======================================================================

一、为什么在这一轮做
  本项目自 0.9.0 起把 core 的「界面零入口」能力一块块接出来：策略、路由组、
  自定义供应商、出图、安全防护。清完这些之后剩下的候选只有两个：
  「真实 Claude Code 客户端接 Anthropic 入口」（本机没客户端，验不了）
  和「数据目录备份 / 恢复」——后者是唯一一直没碰过的运维面。
  凭证全在 `secure/` 下且被 `master.key` 加密，一旦误删就是 13 个账号加
  115 个模型目录全部重登，这正是需要快照的地方。

二、五个端点（`server/.../BackupManager.kt` + `UiRoutes.kt`）
  GET  /ui/backup           列表 + 范围 + 待恢复 + 上次恢复结果
  POST /ui/backup/create    创建（`includeCallLogs` 可选，默认带）
  POST /ui/backup/delete    删除单份
  POST /ui/backup/restore   登记一次恢复（**不动任何现有文件**）
  POST /ui/backup/cancel    取消已登记的恢复

三、五个设计决定（每条都对应一个会被踩的点）

  1. 备份目录在数据目录**之外**（`<dataDir>/../backups`）。
     放里面的话，「先清空再解压」那一步会把备份自己删掉——用户就失去了唯一的回滚点。

  2. 白名单制，不是整目录打包。
     不含 `webview2/`：Chromium 缓存实测 80 MB，与本项目数据无关，
     混进去一次备份从 2 MB 变 80 MB，用户不会再用第二次。
     也不含 `.instance.json`（写死旧端口与派生标记）、`.update-cache.json`、
     `shell-launcher.log`（可再生的进程状态）。
     实测正式数据：171 个条目 / 2.3 MB（含调用记录全文）；不含时 69 个 / 70 KB。

  3. 恢复是**两段式**：端点只写 `.restore-pending.json`，真正替换在下次启动。
     正在跑的进程持有 `secure/` 下的文件句柄，边跑边替换会读到半个账号池；
     换完不重启，内存里也还是旧账号池（表现成「恢复了但界面没变」）。
     `Main.kt` 在**拿到实例锁之后、EngineHost 构造之前**调 `applyPending()`：
     那时旧进程确实不在了，加密存储也还没打开。

  4. 顺序是「**先解压、后清空**」，不是「先清空、后解压」。
     第一版写成了先删后解，一旦包读到一半失败，数据目录已经空了——
     用户看到的是「恢复失败，账号全没了」。现在先解到
     `dataDir/.restore-staging/`（在白名单之外，不会被清理误伤），
     全部落盘成功后才清现有条目、再同盘搬入。中途任何一步失败，
     现有数据一个字节都没动，pending 保留、下次启动还能重试。

  5. 恢复前**强制**再快照一份（`pre-restore` 回滚包）。
     快照失败就整体放弃恢复。没有回滚点的替换不接受。

四、抓出并修掉的三个真 bug
  ① 同一秒连点两次「立即备份」→ 文件名相同 → 第二份覆盖第一份。
     根因：`renameTo` 在目标已存在时不覆盖（Windows 返回 false），
     随后的 `copyTo(overwrite=true)` 就把上一份写掉了。实测连点三次只剩两份。
     修法：`uniqueName()` 撞名时追加 `-2`、`-3`。
  ② 列表按文件名字典序排 → `…-1549-2.zip` 排到 `…-1549.zip` **前面**（`-`=45 < `.`=46）。
     修法：按清单里的 `createdAtMillis` 排，读不到才回落文件 mtime。
  ③ 创建日志打印两遍（`applyPending` 自己 println 一次，`Main.kt` 又把返回值打一次）。
     修法：只由 Main 打一次。

五、界面（`web/dist/app.js` 的 `renderBackup()`）
  · 第 13 项侧栏入口「备份与恢复」。实测 nav-scroll content=420 / client=420、
    末项 bottom=423 < footTop=641，**没有溢出**（同一组内多一项没加组标题，

## 六·Q 流式保真度与脱敏还原的可证伪验证（2026-11-20）

本轮不加功能，只补「证据」：把「流式透传已经修好了」从一句结论，变成三条外部可复算的判据。
全部通过，未改任何生产代码。

### 1. 差分对照组（core/src/test/.../StreamFidelityTest.kt，3 用例）

判据是哈希，不是判断：

- 路径 A：脱敏关 → 上游看到原文 → 客户端收到原文
- 路径 B：脱敏开 → 上游看到占位符 → 网关还原 → 客户端收到原文

`sha256(A) == sha256(B)` 且 `== sha256(原文)`。占位符泄漏一个字符、少还原一个字符、
尾巴被丢弃，哈希立刻不同。文本以 `__AIGW` 结尾，专门逼出「flush 丢尾巴」这类错。

两条不依赖期望值的旁证：客户端内容不含 `__AIGW_`；上游收到的内容含 `__AIGW_` 但不含原始密钥
（证明脱敏真生效，而不是没脱敏导致对照组"碰巧相等"）。

另有**穷举切点**：把脱敏后文本里的每个占位符，按它的每一个字节位置各切一次
（每次切成两帧各跑一遍完整 HTTP 链路），逐一断言还原后哈希仍等于原文。
手工挑三个切点验不出只在特定边界出现的 bug，这一条能。

### 2. 故障注入矩阵（tools/uitest/chaos_stream.py，7 模式）

自起一个可编程故障上游 + 一个干净实例（真实进程，`--data .tmp/chaos/data`），
期望行为事先写死，不跑完再补文档：

| 模式 | 上游动作 | 客户端必须看到 |
|---|---|---|
| ok | 正常两帧 + [DONE] | 200、逐字节一致、无占位符 |
| rate429 | 首响应 429 | 429 + `rate_limit_exceeded`（不伪装成 503） |
| server500 | 首响应 500 | 502 + `upstream_error` |
| half | 发半截后直接断 socket | 已发出的半截 + 终止帧 + **0 坏帧**（不是裸断流） |
| drip | 每字符一帧、帧间 50ms | 内容完整、首字延迟 < 5s（证明没攒包） |
| bigchunk | 单 delta 塞 96KB | 90129 字符未被截断 |
| splitph | 把占位符劈在两帧之间 | 拼回原文、哈希一致、不泄漏 |

7 模式全 PASS。末段对照组同样给出 `36e8197c…` 两侧相等。

坑两条（都写进脚本注释）：① 模式会互相污染——500 把唯一供应商打到熔断后，
后续模式全拿到「熔断隔离中，直接跳过」，验的就不是那个故障了，所以脚本先把
`failureThreshold` 抬到 100、`maxAttempts` 压到 1；② 手写解 chunked 把 `content`
切成 `connt`，哈希对照变成"碰巧不等"，改用标准库 `http.client` 的 `readline`。

### 3. 变异测试（tools/uitest/mutate_redactor.py，3 变异）

对 `PrivacyRedactor` 手工种三个真实错，验证测试网确实会红——只绿不红的测试等于装饰：

| 变异 | 内容 | 结果 |
|---|---|---|
| M1 | 回看上限 `maxPlaceholderLength - 1`（原实现的坑） | 2 个失败用例 |
| M2 | `flush()` 直接返回空串 | 2 个失败用例 |
| M3 | `restore()` 漏掉最后一条映射 | 6 个失败用例 |

跑完无条件恢复并校验 sha256 与备份一致（`c56d8929…` 不变）。
M2 第一次没被抓住——因为原文没有以占位符前缀结尾的样本，`flush` 根本没东西可交。
补上 `第六段：…__AIGW` 之后才变红。这条正是「测试网为何需要变异测试」的现场证据。
